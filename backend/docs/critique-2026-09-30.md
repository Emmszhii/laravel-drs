# Critique of the paper and the system (2026-09-30)

Scope: Chapters I–III in the "Copy of Revised of Chapter 1 to 3" tab, and the code on `trim-to-paper-scope` (solver service, Laravel backend, React frontend). Tests at the time of review: backend 189 passed, solver 23 passed, frontend typecheck clean.

**Verdict:** the core design holds up, but the evaluation doesn't yet support the paper's claims, and the offline and sync code has gaps a hostile or careless user could hit.

## The paper

### Main weaknesses

1. **The main comparison is against a baseline nobody uses.** The office has no formula (Chapter I says so), yet Objective 2's success test is beating the flat 1.5 rule. Make the office's own past orders the main comparison where the records have them, and keep 1.5 as a secondary one.
2. **The backtest is too small to settle anything.**
   - 12 quarters at most (Q3 2023–Q2 2026), with scoring from the 5th, gives 4–8 test quarters. "Better in a majority" can mean winning 3 of 4.
   - Early test quarters have only 4–7 earlier quarters to learn from, but Table 4 assumes 8 ("M = 8"), and Data Collection says at least 8 quarters are needed.
   - Kristine/Leon falls in Q4 2024, the 6th quarter, so it is tested with no earlier typhoon quarter to learn from. "Typhoon quarters reported separately" is probably one data point that every rule fails.
   - Say these things outright, state that each rule carries its own leftover stock, and state where each past quarter's budget Bₜ comes from.
3. **The person who approves isn't tested on the explanations.** The Head of Office reads and approves the recommendation, but the explanation task tests only Logistics and Research and Planning. The task also asks about "₱20,000 more", while the dashboard shows "the next ₱10,000".
4. **The weighted-sum objective always cuts the expensive items first.** In the worked example, food packs end up 42% short while water and hygiene kits are fully covered. Explain why a weighted sum was chosen, and that the priority weights are how the office prevents this.
5. **The depot space constraint counts stock twice.** Σvᵢ(qᵢ + xᵢ) ≤ V uses V = *free* space, which already excludes the stock on hand. Use Σvᵢxᵢ ≤ V, or define V as total capacity. The code does the same (`solver-service/app/solvers/replenishment.py:114`).
6. **The hash chain is filed under the wrong quality characteristic.** Tamper evidence is ISO 25010 *Security* (integrity, accountability), not *Safety – fail safe*. The paper evaluates Safety and skips Security.
7. **The title promises something the scope excludes.** "…for disaster response" suggests live operations, which the scope excludes (Chapter I redefines "response" as readiness).

### Where the paper contradicts itself or the system

- Table 3 says `budget_amount` is "entered by Logistics". Everywhere else, and in the system, the Head of Office enters it.
- The Table 4 note and the "Policy choices" limitation say Logistics sets the VED weights. In the system the Head of Office confirms them.
- "Money is left over only when every target is met" can't hold with whole-number orders. Up to one unit's price can be left over.
- The "effectiveness" property, in the textbook algorithm sense, means each step is basic enough to carry out, not that the result beats the current rule.
- The tense is mixed ("will be conducted" / "uses").
- The spike check needs a definition of "usual" use (a median would hold up better).

The worked example checks out: 127/240/350 spending ₱200,000; 218/159/232 at 23/27/20% short, spending ₱199,450; and ₱10,000 buys 20 food packs, 42%→38%. Chapter II's gap argument and Table 1's "ND" caveat are careful and easy to defend.

## The system

### Critical

1. **The offline queue belongs to no one.** Entries saved offline sync under whoever is signed in next, and logout clears nothing. The cached ICS and borrowed-items pages keep borrower names and contacts after logout. Fix: store the user on each outbox item and sync only that user's items; clear the `offline-pages` cache and warn on logout; treat a 403 as "keep queued".
2. **The sync endpoint trusts the device's quantity and sign.** A `release` sent with a positive number reduces the line's released count. An `issue` with quantity 5 creates one borrowed unit but removes 5 from stock. Fix: validate by reason (`Api/StockController.php`).
3. **Anyone who can file a request can inflate the solver's demand.** Rejected requests still count as history (`QuarterHistory.php:34`). The request date can be set to any date, and quantities have no maximum.
4. **The solver accepts negative history and duplicate item IDs.** Negative history makes the model unbounded, and the result is reported as a valid plan. Duplicate item IDs crash CBC and return a 500.
5. **One bad entry blocks the whole sync batch, and failed entries can't be retried.** A 4xx from the server marks every entry in the batch failed. An exception partway through returns a 500 after some entries have saved, and the device retries forever. Fix: per-entry results, plus Retry and Discard buttons.

### Major

- **Budget curve when a solve is infeasible:** the solver returns shortage 0, and carrying the best result forward turns that into a flat line at 0. An infeasible solve also drops every planned item from the response. The "never rises" tests can't fail because of the carry-forward.
- **Runs stuck in "queued":** `RunReplenishmentJob` has no timeout and no `failed()` method. The worker kills jobs at 60 s, but a solve plus the curve can take longer, so the run stays "queued" forever.
- **Ledger lock on Postgres:** the lock is taken inside callers' database transactions and uses the database cache store, which gives 500 errors under contention. Use `pg_advisory_xact_lock` inside `append`. The tests run on SQLite with an array cache, so this is untested.
- **Stage 2 and new items:** short histories are padded with zeros, which understates a new item's expected shortage. The cold-start rule is skipped in Stage 2.
- **Covering level with short history:** the level keeps the k-th rank from 8 quarters, so with fewer quarters it covers less than the VED share.
- **Some reasons aren't read from the solution:** an item can say "budget ran out" when the budget isn't binding.
- **Double-clicks:** Save entry, Release, Approve and Close have no busy state. Concurrent releases can also exceed what was approved, because nothing locks the request row.
- **Login and debug settings:** login has no rate limit, and `.env.production` has `APP_DEBUG=true`.
- **Offline page caching:** pages are only cached on a full page load. Moving between pages with the sidebar links never caches `/stock`.
- **Tamper evidence:** deleting the newest rows passes `verify()`, and a failed nightly check alerts no one.
- **Crashes and silent failures:**
  - Resolving an "approvals exceed stock" conflict with a correction crashes (the conflict has no stock entry).
  - Importing the same CSV twice doubles the history.
  - CSV row errors never reach the screen (the page reads `err.response`).
- **Permission flags don't match the role rules:** the Admin can't approve their own request in the UI (`!own`), and can't resolve conflicts (`Web\StockController` sets `resolve` for Logistics only).

### Minor

- **Dashboard wording:**
  - Targets have no units, the chart's y-axis has no label, and the current budget isn't marked on the chart.
  - Backtest details sit in tooltips, which don't show on phones.
  - The header shows jargon like "V 3/4 ×3".
- **Light theme:** borders and green/blue text disappear on the light background.
- **Inputs:** many rely on the placeholder alone and have no label.
- **Time zone:** it's set to UTC, so quarter boundaries are 8 hours off from PH time.
- **Device clocks are trusted:** a device clock set in the future flags every later entry for that item.
- **Solver service:** it has no authentication, sits on the shared Coolify network, runs as root in its container, and only PuLP is pinned among its dependencies.

### What's strong

- **The ledger design is right:** entries are only ever added and the database refuses edits; device IDs and sequence numbers are unique; the fingerprint uses canonical JSON; conflicts are stored separately; offline issue→return ordering works.
- **Borrower privacy is enforced on both the API and the pages, and it's tested.**
- **Stage 1 and Stage 2 match the formulation exactly,** and the worked example is a real test against the actual solver.
- **The backtest has no look-ahead:** each rule carries its own leftover stock.
- **The code is small and readable.**
